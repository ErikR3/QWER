# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

QWER is a C#/.NET 10 game project (SFML.Net for rendering/windowing) built around a hand-rolled, sparse-set-based Entity Component System. It is a **portfolio piece for job applications** — favor correctness and clean, performant design (sparse-set / dense-array patterns) over quick hacks, since this code is meant to be shown to employers.

## Coaching mode

This repo is a learning project. The user is using it to learn ECS design and game programming, not just to ship features. **Do not write or edit code in this project unless explicitly asked to.** Act as a coach:

- Explain concepts (ECS patterns, sparse sets, cache locality, why a design choice matters) in plain terms, using this codebase's actual files/types as concrete examples.
- Ask guiding questions and point at *where* to look (file, pattern, prior art in the repo) rather than supplying the implementation.
- When the user shares code or an approach, give feedback on correctness/design and explain the reasoning, but let them make the edit.
- It's fine to write small illustrative pseudocode or snippets *outside* the project files to demonstrate a concept, if that aids understanding.
- If the user explicitly asks you to write/edit code ("just write it", "implement this"), you may — but default back to coaching mode afterward.
- Performance/efficiency is a core learning goal, not an afterthought: when coaching, actively surface the *why* behind data-oriented design choices — cache locality, memory layout (AoS vs SoA), avoiding allocations/boxing on hot paths, sparse-set vs dictionary tradeoffs, branch/iteration cost. When reviewing the user's code or design, call out inefficient patterns and explain the underlying concept (not just "this is slow" — *why* it's slow and what mental model avoids it next time).

## Architecture

The ECS follows the classic Entity/Component/System split (EntityManager / ComponentManager / ComponentStorage / SystemManager / Coordinator), with **every core manager using a sparse set** (parallel `sparse[]` / dense `[]` arrays with swap-and-pop removal) rather than `Dictionary`-based storage, for cache-friendly iteration and O(1) add/remove. New code should follow this same sparse-set pattern rather than introducing dictionary-based storage on the hot path.

- **`EntityManager.cs`** — owns entity ids as a sparse set (`sparse[entityId] -> dense index`, `dense[index] -> entityId`). Fully implemented: `AddEntity` (allocates and returns the new id), `RemoveEntity` (swap-and-pop), lookups. Entity id allocation/recycling is a second sparse-set-style structure, `unUsedId`/`freeCount`, acting as a LIFO free-list (`freeCount` = count of currently-free ids, invariant mirrors `dense`/`denseCount`: valid free ids live on `unUsedId[0 .. freeCount-1]`, top of stack at `freeCount-1`). `GetFreeId()` (private) pops from it; `RemoveEntity` pushes the freed id back. All O(1), no scanning. `ValidateIdInRange(entityId)`/`ValidateIdInUse(entityId)` are public bool predicates (no throwing) that `RemoveEntity` and `Coordinator` both call to check bounds and liveness before touching the sparse/dense arrays — `RemoveEntity` throws `ArgumentOutOfRangeException`/`InvalidOperationException` itself based on their result.
- **`ComponentStorage.cs`** — defines `IComponentStorage` (non-generic: `HasComponent`/`RemoveComponent`/`GetEntities`) and `ComponentStorage<T> where T : struct`, a generic per-component-type sparse set holding a dense `T[]` parallel to a dense entity-id array. This is where actual component data lives. The non-generic interface exists specifically so `ComponentManager` can hold heterogeneous `ComponentStorage<T>` instances in one collection and call `GetEntities`/`HasComponent` on them without knowing the concrete `T`.
- **`ComponentManager.cs`** — not a storage class itself; it's a type-keyed registry (`Dictionary<Type, IComponentStorage>`) that lazily creates one `ComponentStorage<T>` per component type and dispatches the generic `AddComponent<T>`/`GetComponent<T>`/`RemoveComponent<T>`/`GetEntitiesWith<T>` calls to it. `EntityDestroyed(entityId)` sweeps an entity out of every registered storage — this must be wired up wherever entities are destroyed to avoid leaking component data. `GetEntitiesWith<T1, T2>()` is a two-component query: it fetches both storages via `GetStorage<T>`, iterates the one with the smaller `GetDenseCount()` (cheaper — fewer entities to check), and filters each id against `other.HasComponent(entityId)` — this is why `GetEntities`/`HasComponent` had to move onto the non-generic `IComponentStorage` interface. Never zips the two dense arrays by shared index; two storages pack entities in independent, unrelated insertion orders, so index `i` in one has no relation to index `i` in the other — entity id via `HasComponent` is the only valid join key between storages.
- **`SystemManager.cs`** — holds a `List<ISystem>` and the shared `Coordinator` instance (passed in via constructor, not self-constructed — it must operate on the same ECS world as the rest of the game, not a private one). `RegisterSystem(ISystem)` appends to the list; `Update(float deltaTime)` runs every registered system's `Update(coordinator, deltaTime)` in registration order (no priority system — order of registration *is* the order of execution, kept deliberately simple/modular).
- **`ISystem.cs`** — the system interface: `void Update(Coordinator coordinator, float deltaTime)`. Systems only ever see the `Coordinator` facade, never `EntityManager`/`ComponentManager` directly, mirroring the layering the rest of the codebase already follows.
- **`Coordinator.cs`** — functional facade over `EntityManager` + `ComponentManager`, wired to `SystemManager` (constructed once in `Program.cs`, shared by reference — the same instance flows into every system's `Update` every frame, so systems always observe the current world state without needing to be "handed" a new `Coordinator`). `CreateEntity()` returns the id `em.AddEntity()` allocates. `DestroyEntity(entityId)` calls `em.RemoveEntity(entityId)` before `cm.EntityDestroyed(entityId)` — that order matters: `RemoveEntity` validates and throws on a bad id, so `ComponentManager` is never touched with an invalid id, and no id is freed back into the pool while its component data still lingers (which would otherwise let a reused id inherit stale components). `AddComponent<T>`/`HasComponent<T>`/`GetComponent<T>`/`RemoveComponent<T>` each validate via `em.ValidateIdInRange`/`ValidateIdInUse` before delegating to the same-named `ComponentManager` call; `GetComponent<T>` returns `ref T` end-to-end (through `ComponentManager`/`ComponentStorage<T>`) so callers mutate component data in place rather than copying the struct. `GetEntitiesWith<T>()` is a thin passthrough to `cm.GetEntitiesWith<T>()` with no id validation, since it queries across all entities rather than acting on one; `GetEntitiesWith<T1, T2>()` passes through `cm`'s two-component query the same way. Both only exist as fixed-arity overloads (2-component) — no variadic/`params Type[]` version, a deliberate YAGNI call until a system actually needs a 3+ component query.
- **`Components/Components.cs`** — plain component `struct`s (`PositionComponent`, `VelocityComponent`, `ControlComponent`, `PlatformerComponent`, `JumpComponent`, `DashComponent`, `SpriteComponent`, `HitboxComponent`, `GravityComponent`, `GroundedComponent`, `PlayerControlledComponent`, `AnimationComponent`, `AnimationSpriteSheets`, `HealthComponent`, `DamageComponent`) in the `Components` namespace. All fields are `public` — components are pure data, and systems need to read/write them through the `ref T` returned by `Coordinator.GetComponent<T>`, so a private field would be unreachable from outside the struct. All component types must be `struct`s (both `ComponentManager` and `ComponentStorage<T>` are constrained to `where T : struct`). `JumpComponent` intentionally uses a `jumpsRemaining`/`maxJumps` counter pair rather than a `bool jumping` flag, so a future double/multi-jump is a data change (`maxJumps = 2`) rather than a system-logic rewrite; a static entity (e.g. a platform) is distinguished from a dynamic one purely by the *absence* of `VelocityComponent`, no marker/tag component needed for that case. `ControlComponent.runHeld` is raw input state (set by `InputSystem` from Shift, alongside `jumpPressed`/`movementDirection`) — deliberately *not* on `AnimationComponent`, so both `AnimationSystem` (pick the Running clip) and `PlatformerSystem` (apply a run speed bonus) can read the same flag without one depending on the other's component. `AnimationState` (`Idle`/`Running`/`Walking`/`Jumping`) + `AnimationComponent` (`facingRight`, `timer`, `frameDuration`, `state`, `frameIndex`, `frameCount`) hold per-entity animation *playback* state; `AnimationSpriteSheets` (`idleTexture`/`walkingTexture`/`runningTexture`/`jumpingTexture` + one `frameCount` each) holds the *data* for which texture/frame-count belongs to each state, kept as a separate component (rather than merged into `AnimationComponent`) so an entity can have animation playback without necessarily using the multi-sheet-per-state model (see `AnimationSystem`'s fallback). `HealthComponent` (`maxHealth`, `currentHealth`, `iFrames`, `isDead`, `stunFrames`) now grew an `iFrames`/`stunFrames` pair beyond the original `maxHealth`/`currentHealth`/`isDead` sketch, consumed by `HealthSystem`. `DamageComponent` (`hpDamage`, `duration`) is a tag-like data component put on hazard/attack entities — an entity "deals damage" purely by having a `DamageComponent` + `PositionComponent` + `HitboxComponent`, no separate attacker/projectile marker needed.
- **`ECSConfig.cs`** — shared constants (`MaxEntities`, `Framerate`), used to size sparse arrays and cap `RenderWindow`'s frame rate.
- **`ECSDebugger.cs`** — console dump helpers (`PrintSets`, `PrintDense`, `PrintSparse`) for inspecting `EntityManager`'s sparse/dense arrays while developing.
- **`Program.cs`** — the real game loop, now with an actual test scene: builds a static platform entity (`PositionComponent`+`HitboxComponent`) and a player entity carrying every gameplay component (`Position`/`Velocity`/`Hitbox`/`Control`/`Jump`/`Grounded`/`Gravity`/`Platformer`/`PlayerControlled`/`Sprite`/`AnimationSpriteSheets`/`AnimationComponent`), loading four SFML `Texture`s (`Assets/Samurai/{Idle,Walk,Run,Jump}.png`) and deriving each animation's `frameCount` from `texture.Size.X / samuraiFrameSize`. Systems are registered on `SystemManager` in a deliberate order — `Gravity` → `Input` → `Jump` → `Platformer` → `Movement` → `Animation` — so that by the time `MovementSystem` integrates position, velocity already reflects gravity, input, jump impulses, and platformer accel/decel for that frame; `JumpSystem` is constructed with `c` directly (`new JumpSystem(c)`) since it needs the `Coordinator` at construction time to seed `validPlatforms`, and platform entities are created before that call so the constructor-time query finds them. `RenderSystem` is *not* registered on `SystemManager` — it's instantiated separately and called explicitly inside the render portion of the loop (`renderSystem.Update(c, window)`), consistent with its non-`ISystem` signature. The `while (window.IsOpen)` loop each frame restarts an SFML `Clock`, converts the elapsed `Time` to seconds via `.AsSeconds()` (Coordinator/`SystemManager.Update` takes `float`, not SFML's `Time`), calls `sm.Update(deltaTime)`, prints a throttled debug line (position/velocity/grounded) every 0.5s via a second `Clock`, then does the SFML event/clear/render/display cycle. SFML.Net is plain C# API (PascalCase, no `sf::`-style C++ namespace aliasing) — easy to reach for C++-SFML syntax by habit; watch for that.
- **`Physics/Collision.cs`** — new static helper class (`Physics` namespace, no state, pure functions over component data) shared by `HealthSystem` and `JumpSystem` so AABB logic lives in one place rather than being duplicated per system. `OverlapsOnXAxis`/`OverlapsOnYAxis` do the standard interval-overlap check (`aLeft < bRight && aRight > bLeft`) against two `PositionComponent`+`HitboxComponent` pairs. `NearGround` is a velocity-aware ground proximity check: it compares `entityBottom` to `platformTop` against a `tolerance` that scales with how far the entity could travel this frame (`Math.Abs(entityVel.y * deltaTime)`, floored at 1% of hitbox height) — this is what lets `JumpSystem` detect "landed" without an entity tunneling through the tolerance band at high fall speed on a slow frame. `IsGrounded` composes `OverlapsOnXAxis` + `NearGround`. No general resolve/response logic yet (e.g. no swept AABB) — deliberately just the overlap/proximity predicates each calling system needs.
- **`Systems/RenderSystem.cs`** — now functional: for each entity with `PositionComponent`+`HitboxComponent` that also has a `SpriteComponent` (checked via `HasComponent`, so entities without a sprite are skipped rather than throwing), it syncs `sprite.sprite.Position` from `PositionComponent` each frame and calls `window.Draw(entitySprite.sprite)`. Still does not implement `ISystem` and still takes `RenderWindow` directly — a deliberate deviation from the `ISystem` signature since drawing needs the SFML window; called explicitly from `Program.cs` rather than through `SystemManager` (see above).
- **`Systems/AnimationSystem.cs`** — now fully implemented. Per entity with `AnimationComponent`+`SpriteComponent`: derives a `direction` and `runHeld` from `ControlComponent` if present, else falls back to `VelocityComponent.x` (so non-player-controlled animated entities still get a facing direction without needing `ControlComponent`) — this fallback is the reason `HasComponent` checks gate each optional read rather than assuming every animated entity is player-controlled. Sets `facingRight` when `|direction|` crosses a small `DirectionThreshold` (avoids flicker-flipping at near-zero velocity/input noise). Picks `AnimationState` via `DetermineState` (Idle if under threshold, else Running/Walking based on `runHeld`) when grounded, or forces `Jumping` when `GroundedComponent.isGrounded` is false (defaults to "grounded" if the entity has no `GroundedComponent` at all). On a state change it resets `frameIndex`/`timer` and, if the entity has `AnimationSpriteSheets`, swaps in that state's texture/frameCount via `ApplyStateTexture`. Every frame it advances `anim.timer` and steps `frameIndex` forward (wrapping mod `frameCount`) once `timer` exceeds `frameDuration`, then `ApplyFrame` slices the sprite sheet horizontally (`textureWidth / frameCount`) into an `IntRect`, using a **negative width** (`-frameWidth`) plus an offset start column to flip the sprite when `facingRight` is false — a common SFML trick to mirror a `TextureRect` without a separate flipped texture or a `Sprite.Scale` hack that would also flip the sprite's origin-relative position.
- **`Systems/GravitySystem.cs`** — per entity with `VelocityComponent`+`GravityComponent`: `vel.y += gravity.acceleration * deltaTime`, then clamps to `gravity.terminalVelocity` via `Math.Min`. Simple, stateless, and — like `MovementSystem` — a good reference example of the "query, get `ref`, mutate in place" system pattern.
- **`Systems/InputSystem.cs`** — per entity with `ControlComponent`+`PlayerControlledComponent`: polls SFML's `Keyboard.IsKeyPressed` directly (Space → `jumpPressed`, LShift → `runHeld`, A/D → `movementDirection` as -1/0/1) and writes the raw state into `ControlComponent`. `PlayerControlledComponent` (an empty marker struct) is what scopes this polling to the actual player entity rather than every entity that happens to have a `ControlComponent` — the tag-component pattern for "this entity is what the human drives," distinct from data components that always carry fields.
- **`Systems/PlatformerSystem.cs`** — per entity with `VelocityComponent`+`PlatformerComponent`: picks a target horizontal velocity and acceleration `speed` based on `GroundedComponent.isGrounded` (ground vs air values from `PlatformerComponent`), then eases `entityVel.x` toward `target` by `speed * deltaTime` per frame (clamped with `Math.Min`/`Math.Max` so it can't overshoot past `target`) rather than snapping directly to it — this is what gives movement acceleration/deceleration "feel" instead of instant velocity changes. Reads `ControlComponent`/`GroundedComponent` by value (not `ref`) since it only reads them here.
- **`Systems/HealthSystem.cs`** — per entity with `HealthComponent`+`HitboxComponent`, checked against every entity with `DamageComponent` (nested loop, same naive-broadphase tradeoff noted under `JumpSystem`): on AABB overlap (via `Physics.Collision`) with `iFrames > 0`, damage is applied via `entityHealth.currentHealth -= dmgDamage.hpDamage`; otherwise, if just `iFrames > 0`, `iFrames` ticks down. **Likely bug worth flagging to the user, not fixing unprompted:** the damage branch and the "not overlapping" cooldown-tick branch are both gated on `iFrames > 0`, so damage is only ever applied *while* `iFrames` is still positive and never resets `iFrames` back up after a hit — as written this reads backwards from the usual invincibility-frames pattern (normally you'd damage when `iFrames <= 0`, then set `iFrames` back to some cooldown value). Doesn't yet touch `maxHealth`/`isDead`/`stunFrames`.
- **`Systems/MovementSystem.cs`** — reference implementation for the system pattern: `coordinator.GetEntitiesWith<PositionComponent, VelocityComponent>()` to find candidates, then per-entity `ref var pos = ref coordinator.GetComponent<PositionComponent>(id);` (note: `ref` is required on *both* sides of the assignment to bind to the ref-return — dropping the second `ref` copies the struct instead) to mutate `Position` by `Velocity * deltaTime` in place. Verified working end-to-end against a live entity.
- **`Systems/JumpSystem.cs`** — now fully implemented; the constructor-injection option from the earlier known bug was the one taken. `JumpSystem(Coordinator coordinator)` builds `validPlatforms` once at construction by querying `HitboxComponent`+`PositionComponent` entities filtered to those *without* `VelocityComponent` — correct here because `Program.cs` creates the platform entity before `new JumpSystem(c)` runs (order-dependent; a platform added later would be invisible to this system, a tradeoff accepted rather than the lazy-init alternative). `Update` per jump-capable entity: resets `isGrounded` to false, then checks every cached platform via `Physics.Collision.IsGrounded`; on the first hit it snaps `entityPos.y` to sit exactly on the platform top, zeroes/clamps downward velocity (`Math.Min(entityVel.y, 0)`), restores `jumpsRemaining = maxJumps`, and `break`s (one ground contact per frame is enough). `JumpTriggered`/`JumpReleased` are edge-detectors comparing `jumpPressed` against `jumpHeldLastFrame` (rising/falling edge) so holding Space doesn't re-trigger a jump every frame; a triggered jump applies `-initialImpulse` to `vel.y` and decrements `jumpsRemaining` (only if `> 0`, enabling double/multi-jump per `JumpComponent.maxJumps`), while a released jump while still ascending (`vel.y < 0`) cuts velocity to 30% for variable jump height. State-transition `Console.WriteLine`s exist for debugging and would be worth stripping or gating behind a debug flag before this is shown as portfolio-clean code. Longer-term collision-broadphase note: naive entity×platform nested-loop collision is fine at current/expected scene entity counts; a spatial hash grid (bucket platforms by cell, only check the cells the moving entity's hitbox overlaps) is the documented next step *if* profiling or scene scale ever makes the naive check a real cost — deliberately not built preemptively.
- **`Assets/Samurai/`** — sprite sheets (`Idle.png`, `Walk.png`, `Run.png`, `Jump.png`) actually wired up and loaded by `Program.cs`/`AnimationSystem`, each sliced into fixed-size frames (`samuraiFrameSize = 128`) by `Texture.Size.X / frameSize`. The earlier `Assets/PNG/` (`Objects/`, `Tiles/`) folder is still unused placeholder art, not yet consumed by any system.
