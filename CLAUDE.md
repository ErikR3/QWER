# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

QWER is a C#/.NET 10 game project (SFML.Net for rendering/windowing) built around a hand-rolled, sparse-set-based Entity Component System. It is a **portfolio piece for job applications** — favor correctness and clean, performant design (sparse-set / dense-array patterns) over quick hacks, since this code is meant to be shown to employers.

## Coaching mode

This repo is a learning project. The user is using it to learn ECS design and game programming, not just to ship features. **Do not write or edit code in this project unless explicitly asked to.** Act as a coach:

- Explain concepts (ECS patterns, sparse sets, cache locality, why a design choice matters) in plain terms, using this codebase's actual files/types as concrete examples.
- Ask guiding questions and point at *where* to look (file, pattern, prior art in the repo) rather than supplying the implementation.
- When the user shares code or an approach, give feedback on correctness/design and explain the reasoning, but let them make the edit.
- It's fine to write small illustrative pseudocode or snippets *outside* the project files to demonstrate a concept, if that aids understanding.
- If the user explicitly asks you to write/edit code ("just write it", "implement this"), you may — but default back to coaching mode afterward.
- Performance/efficiency is a core learning goal, not an afterthought: when coaching, actively surface the *why* behind data-oriented design choices — cache locality, memory layout (AoS vs SoA), avoiding allocations/boxing on hot paths, sparse-set vs dictionary tradeoffs, branch/iteration cost. When reviewing the user's code or design, call out inefficient patterns and explain the underlying concept (not just "this is slow" — *why* it's slow and what mental model avoids it next time).

## Architecture

The ECS follows the classic Entity/Component/System split (EntityManager / ComponentManager / ComponentStorage / SystemManager / Coordinator), with **every core manager using a sparse set** (parallel `sparse[]` / dense `[]` arrays with swap-and-pop removal) rather than `Dictionary`-based storage, for cache-friendly iteration and O(1) add/remove. New code should follow this same sparse-set pattern rather than introducing dictionary-based storage on the hot path.

- **`EntityManager.cs`** — owns entity ids as a sparse set (`sparse[entityId] -> dense index`, `dense[index] -> entityId`). Fully implemented: `AddEntity` (allocates and returns the new id), `RemoveEntity` (swap-and-pop), lookups. Entity id allocation/recycling is a second sparse-set-style structure, `unUsedId`/`freeCount`, acting as a LIFO free-list (`freeCount` = count of currently-free ids, invariant mirrors `dense`/`denseCount`: valid free ids live on `unUsedId[0 .. freeCount-1]`, top of stack at `freeCount-1`). `GetFreeId()` (private) pops from it; `RemoveEntity` pushes the freed id back. All O(1), no scanning. `ValidateIdInRange(entityId)`/`ValidateIdInUse(entityId)` are public bool predicates (no throwing) that `RemoveEntity` and `Coordinator` both call to check bounds and liveness before touching the sparse/dense arrays — `RemoveEntity` throws `ArgumentOutOfRangeException`/`InvalidOperationException` itself based on their result.
- **`ComponentStorage.cs`** — defines `IComponentStorage` (non-generic: `HasComponent`/`RemoveComponent`/`GetEntities`) and `ComponentStorage<T> where T : struct`, a generic per-component-type sparse set holding a dense `T[]` parallel to a dense entity-id array. This is where actual component data lives. The non-generic interface exists specifically so `ComponentManager` can hold heterogeneous `ComponentStorage<T>` instances in one collection and call `GetEntities`/`HasComponent` on them without knowing the concrete `T`.
- **`ComponentManager.cs`** — not a storage class itself; it's a type-keyed registry (`Dictionary<Type, IComponentStorage>`) that lazily creates one `ComponentStorage<T>` per component type and dispatches the generic `AddComponent<T>`/`GetComponent<T>`/`RemoveComponent<T>`/`GetEntitiesWith<T>` calls to it. `EntityDestroyed(entityId)` sweeps an entity out of every registered storage — this must be wired up wherever entities are destroyed to avoid leaking component data. `GetEntitiesWith<T1, T2>()` is a two-component query: it fetches both storages via `GetStorage<T>`, iterates the one with the smaller `GetDenseCount()` (cheaper — fewer entities to check), and filters each id against `other.HasComponent(entityId)` — this is why `GetEntities`/`HasComponent` had to move onto the non-generic `IComponentStorage` interface. Never zips the two dense arrays by shared index; two storages pack entities in independent, unrelated insertion orders, so index `i` in one has no relation to index `i` in the other — entity id via `HasComponent` is the only valid join key between storages.
- **`SystemManager.cs`** — holds a `List<ISystem>` and the shared `Coordinator` instance (passed in via constructor, not self-constructed — it must operate on the same ECS world as the rest of the game, not a private one). `RegisterSystem(ISystem)` appends to the list; `Update(float deltaTime)` runs every registered system's `Update(coordinator, deltaTime)` in registration order (no priority system — order of registration *is* the order of execution, kept deliberately simple/modular).
- **`ISystem.cs`** — the system interface: `void Update(Coordinator coordinator, float deltaTime)`. Systems only ever see the `Coordinator` facade, never `EntityManager`/`ComponentManager` directly, mirroring the layering the rest of the codebase already follows.
- **`Coordinator.cs`** — functional facade over `EntityManager` + `ComponentManager`, wired to `SystemManager` (constructed once in `Program.cs`, shared by reference — the same instance flows into every system's `Update` every frame, so systems always observe the current world state without needing to be "handed" a new `Coordinator`). `CreateEntity()` returns the id `em.AddEntity()` allocates. `DestroyEntity(entityId)` calls `em.RemoveEntity(entityId)` before `cm.EntityDestroyed(entityId)` — that order matters: `RemoveEntity` validates and throws on a bad id, so `ComponentManager` is never touched with an invalid id, and no id is freed back into the pool while its component data still lingers (which would otherwise let a reused id inherit stale components). `AddComponent<T>`/`HasComponent<T>`/`GetComponent<T>`/`RemoveComponent<T>` each validate via `em.ValidateIdInRange`/`ValidateIdInUse` before delegating to the same-named `ComponentManager` call; `GetComponent<T>` returns `ref T` end-to-end (through `ComponentManager`/`ComponentStorage<T>`) so callers mutate component data in place rather than copying the struct. `GetEntitiesWith<T>()` is a thin passthrough to `cm.GetEntitiesWith<T>()` with no id validation, since it queries across all entities rather than acting on one; `GetEntitiesWith<T1, T2>()` passes through `cm`'s two-component query the same way. Both only exist as fixed-arity overloads (2-component) — no variadic/`params Type[]` version, a deliberate YAGNI call until a system actually needs a 3+ component query.
- **`Components/Components.cs`** — plain component `struct`s (`PositionComponent`, `VelocityComponent`, `ControlComponent`, `PlatformerComponent`, `JumpComponent`, `DashComponent`, `SpriteComponent`, `HitboxComponent`, `GroundedComponent`, `PlayerControlledComponent`, `AnimationComponent`) in the `Components` namespace. All fields are `public` — components are pure data, and systems need to read/write them through the `ref T` returned by `Coordinator.GetComponent<T>`, so a private field would be unreachable from outside the struct. All component types must be `struct`s (both `ComponentManager` and `ComponentStorage<T>` are constrained to `where T : struct`). `JumpComponent` intentionally uses a `jumpsRemaining`/`maxJumps` counter pair rather than a `bool jumping` flag, so a future double/multi-jump is a data change (`maxJumps = 2`) rather than a system-logic rewrite; a static entity (e.g. a platform) is distinguished from a dynamic one purely by the *absence* of `VelocityComponent`, no marker/tag component needed for that case. **New, not yet consumed by any system:** `AnimationState` enum (`Idle`/`Running`/`Walking`) and `AnimationComponent` (`facingRight`, `timer`, `frameDuration`, `state`, `frameIndex`, `frameCount`) — the data shape for sprite-sheet animation (frame timing via `timer`/`frameDuration`, current frame via `frameIndex`/`frameCount`, horizontal flip via `facingRight`), laid out for an `AnimationSystem` to drive.
- **`ECSConfig.cs`** — shared constants (`MaxEntities`, `Framerate`), used to size sparse arrays and cap `RenderWindow`'s frame rate.
- **`ECSDebugger.cs`** — console dump helpers (`PrintSets`, `PrintDense`, `PrintSparse`) for inspecting `EntityManager`'s sparse/dense arrays while developing.
- **`Program.cs`** — the real game loop: creates `Coordinator`/`SystemManager` once before the loop, registers systems, then `while (window.IsOpen)` each frame restarts an SFML `Clock`, converts the elapsed `Time` to seconds via `.AsSeconds()` (Coordinator/`SystemManager.Update` takes `float`, not SFML's `Time`), calls `sm.Update(deltaTime)`, then does the SFML event/clear/display cycle. SFML.Net is plain C# API (PascalCase, no `sf::`-style C++ namespace aliasing) — easy to reach for C++-SFML syntax by habit; watch for that.
- **`Systems/RenderSystem.cs`** — **in progress, not yet functional.** `Update(coordinator, window)` queries `PositionComponent`+`HitboxComponent` and, per entity, currently only fetches `ref SpriteComponent` and `ControlComponent` (the latter by value, not `ref` — fine for now since it's unused, but worth revisiting once the system actually reads control state) without doing anything with them yet; no `window.Draw(...)` call exists. Takes `RenderWindow` directly rather than only `Coordinator`+`deltaTime` like other systems, since drawing needs the SFML window — a deliberate deviation from the `ISystem` signature, presumably called separately in `Program.cs` rather than through `SystemManager`.
- **`Systems/AnimationSystem.cs`** — new file, currently empty. Intended home for logic that drives `AnimationComponent` (advance `timer`/`frameIndex` by `frameDuration`, switch `state`, flip on `facingRight`) and presumably feeds the resulting frame/flip into `SpriteComponent` for `RenderSystem` to draw.
- **`Assets/PNG/`** — new asset folder (`Objects/`, `Tiles/`) with sprite art, added ahead of `AnimationSystem`/`RenderSystem` being wired up to use it.
- **`Systems/MovementSystem.cs`** — reference implementation for the system pattern: `coordinator.GetEntitiesWith<PositionComponent, VelocityComponent>()` to find candidates, then per-entity `ref var pos = ref coordinator.GetComponent<PositionComponent>(id);` (note: `ref` is required on *both* sides of the assignment to bind to the ref-return — dropping the second `ref` copies the struct instead) to mutate `Position` by `Velocity * deltaTime` in place. Verified working end-to-end against a live entity.
- **`Systems/JumpSystem.cs`** — **in progress, not yet functional.** Currently queries jump-capable entities (`JumpComponent`+`PositionComponent`) and platform entities (`HitboxComponent`+`PositionComponent`, filtered to those *without* `VelocityComponent`), but the actual "is this entity standing on top of this platform" AABB check and the jump-trigger/`jumpsRemaining` logic are not yet written. **Known bug to fix:** the platform list was moved to a `private List<int> validPlatforms` field to avoid rebuilding it every frame (platforms are static), but the population loop that fills it still runs unconditionally inside `Update` every frame and is never cleared first — it re-appends the same ids each frame, growing `validPlatforms` unbounded (unbounded memory growth, plus duplicate/redundant collision checks). Needs either constructor injection of `Coordinator` (build the cache once at construction — but only correct if platform entities already exist before `new JumpSystem(coordinator)` runs) or a lazy one-time build guarded by an `initialized` flag inside `Update` (order-independent, since it defers building until the first real frame). Longer-term collision-broadphase note: naive entity×platform nested-loop collision is fine at current/expected scene entity counts; a spatial hash grid (bucket platforms by cell, only check the cells the moving entity's hitbox overlaps) is the documented next step *if* profiling or scene scale ever makes the naive check a real cost — deliberately not built preemptively.
